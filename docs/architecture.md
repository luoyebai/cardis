# Cardis 0.3 架构与规则边界

## 数据流

```text
客户端 / CLI
  │ canCast / canAttack / canMove（查询）
  │ cast / attack / move / pass（命令）
  ▼
Game（唯一状态写入者）
  ├─ 校验 → 支付费用或疲劳 → 入栈
  ├─ 双方让过 → 结算一个对象或推进阶段
  ├─ 重新校验目标 → 伤害 / 治疗 / 护盾 / 召唤
  └─ 状态动作：死亡、胜负 → GameState / 顺序日志

JSON → Catalog / Roster 校验 → Cordis cardis.match → Game + CharacterRoster
```

核心仅依赖标准库，内容层使用 JSON，运行时适配 Cordis，客户端使用图形库。
Cordis 不决定规则顺序；服务卸载不等同于撤销游戏效果。同一 Game 只应由一个线程提交命令。

## 开局与回合

固定种子洗牌，每位玩家 15 种适用定义各两张，各抽 4 张。角色初始生命也是最大生命，配置中的 max_mana 为灵力最终上限。
当前上限从 0 开始，先手开始第一个回合后为 1。每个己方回合开始增加上限、恢复灵力、恢复就绪并抽一张，先手第一回合跳过抽牌。
开始处理为自动步骤，无独立响应窗口，之后 MAIN → COMBAT → END → 对方 MAIN。
END 离开时自动从右端弃置到 8 张。护盾及伤害跨回合保留。
起始牌组、固定种子、自动弃牌是首版简化，无开局换牌或组牌 UI。重开复现初始状态；Game 可通过种子参数建立其他对局。

## 战场与结算

每人前后排各三个位置。卡牌索引标识定义，UnitState.id 标识场上具体对象；Target 含玩家及单位 ID，0 表示玩家。
单位 ID 在同一对局内不复用，旧目标不能命中新召唤对象。技能与攻击共用 LIFO 栈。
行动者保留优先权，双方连续让过只结算一个对象，然后主动玩家获得优先权。角色牌只能自己主要阶段空栈施放，技能可在任何持有优先权的时点施放。
攻击只在己方战斗阶段空栈声明，先疲劳，结算时重新校验攻击者及目标。失效不返还费用或行动次数。
前排阻挡普通攻击，前排守护优先；后排仍能被技能选择。角色战斗同时伤害，之后处理死亡。
疾奏仅豁免对角色攻击的登场等待。移动需就绪并度过登场等待，每人每回合一次，移动后疲劳。
同一作品角色不能在同一方重复存在，通用角色可有多个实例。治疗不超过最大生命，护盾先抵伤害。
生命归零或需要抽牌却无牌时失败。GameState 的 winner 和 result 保存终局结果。

## 多段技能与延迟队列

CardDefinition.effects 保存 1–4 个 EffectStep，包含 effect、amount、timing、recipient。
ON_RESOLVE 表示原技能响应窗口关闭后执行；END_OF_TURN 表示原技能结算时登记为 ScheduledEffect。
SELECTED 捕获原选择目标，CONTROLLER / OPPONENT 分别指向施放者 / 对方玩家，支持“伤害敌人，同时给自己登记治疗”。
一个技能至少有一段 SELECTED 效果，所有 SELECTED 段必须使用同一友方或敌方目标；目前不支持每段分别选目标。
effects 为空的 C++ 旧定义由 EffectsOf 规范化为单段即时效果；JSON 中使用 effects 时不能同时声明旧 effect / amount。

原技能目标在首次结算前失效时，整张技能失效，不登记延迟效果。首次结算有效时，所有即时段依定义顺序执行，然后进行状态动作；延迟段保留捕获的目标 ID。
延迟段登记后与原技能卡牌分离，卡牌进入墓地。之后目标离场，延迟段仍按时入栈，但结算时失效，不转移到玩家或新入场对象。

COMBAT → END 时只收集一次 due_turn 已到的效果：主动玩家的组先入栈，再放非主动玩家的组，因此非主动玩家组先结算。
同一玩家按登记先后结算；本版固定排序，不开放触发顺序选择。每个 TRIGGER 仍需双方让过才能结算，效果不可再次排期、扣费或把同一张牌再次送墓地。
在 END 阶段才登记的效果 due_turn 为下一回合；普通阶段登记的效果在本回合结束阶段到期。
攻击继续在战斗阶段响应后结算，不加入延迟列表。

## 呈现时间与规则时间

引擎只依据命令、回合号和阶段，没有秒表或帧时间。客户端的阶段短提示与 3 秒回合交接遮罩只控制绘制和输入。
交接遮罩期间阻止对局命令，可显式跳过；倒计时结束不调用 pass 或其他游戏命令。终局会取消交接提示，优先显示胜负。
客户端按可执行命令突出手牌、角色、合法目标；主按钮文案随阶段和确认次数改变，但始终只提交当前玩家一次 pass。

## 界面动效层

apps/client/effects.hpp / effects.cpp 是纯状态与数学模块：缓动曲线、可重定向过渡、一次性时钟、粒子池、飘字、
冲击环与光束、震屏与闪屏。它只使用 raylib 的类型，不调用任何 raylib 绘制函数，因此 tests/client_test.cpp
可以在没有图形上下文时验证曲线端点与单调性、过渡的帧率无关性与重定向连续性、粒子上限、震屏衰减与几何约束。
apps/client/layout.hpp 是界面几何的唯一来源，测试用同一组矩形断言控件不越出画布、血条与灵力格不互相重叠。

每帧的顺序是：advance 推进入场与计时，observe 对比 GameState 快照，随后绘制并回报控件位置，最后绘制覆盖层。
对比的字段是双方生命、护盾、灵力、单位生命与护盾、栈深度、回合和阶段；差值转成受伤闪红与飘字、召唤入场、
退场溶解、落败震屏、结算光束、交接与终局庆祝。正在阅读的数值本身不移动，只有血条、灵力格与进度做缓动；
文本位置与全局位移都取整像素，保证字体图集始终对齐。

动效预算：按压与悬停 100–160ms，入场 220–240ms，弹层 200ms 内完成，遮罩行按 40ms 递进且总延迟有上限，
不出现超过 300ms 的可交互动效。`--no-fx` 或界面中的 F 键切换低动效模式：保留颜色、透明度与状态变化，
去掉位移、震屏、粒子和飘字上升，`EffectSettings::motion` 是唯一的开关。

## 测试与复现

CTest 包含规则行为、严格清单/角色关联、Cordis 生命周期及实际起始牌组完整模拟。
CLI 的固定行动策略有步数上限，未完成对局会报错；这不是正式 AI。
窗口 smoke 模式通过规则命令建立展示场景，渲染后退出；--smoke-small 检查小窗口，--smoke-battle 检查战场。
smoke 帧使用固定步长推进呈现时钟，因此截图落在动效结束、倒计时已推进的状态上。

## 字体

直接绘制系统 framebuffer，用 Camera2D 变换布局。字体图集按真实像素字号和 DPI 缓存，点采样与像素对齐。
正文最低逻辑字号 18，小窗口有物理字号下限。长文案换行或省略，不无限缩小。
界面不按帧改变字号：动画只改位置与透明度，否则字体缓存会被逐帧新建。

改动界面或卡牌文案后运行 `python3 tools/update_glyphs.py`（Windows 也可用 tools/update_glyphs.ps1），
它会重写 assets/fonts/glyphs.txt，并逐个字符校验字体 cmap；缺少字形会直接报错，而不是在界面里渲染成方框。
